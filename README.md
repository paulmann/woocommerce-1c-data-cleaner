## Зачем это нужно

При обмене WooCommerce с 1С плагин хранит служебные привязки в метаполях и опциях WordPress: GUID номенклатуры (`_id_1c`), массивы цен по типам цен (`_all_prices`), остатки по складам (`_separate_warehouse_stock`) и служебные карты соответствий в `wp_options`. Со временем эти данные расходятся с учётной системой, и возникают классические симптомы:

- товары дублируются при выгрузке, потому что GUID «залип» на неправильной записи;
- цены не обновляются или показываются от старого типа цен, удалённого в 1С;
- остатки «прилипли», товары висят в статусе «Нет в наличии» либо, наоборот, доступны к заказу;
- в списках «Типы цен» и «Остатки по складам» остаются несуществующие элементы;
- перед переносом магазина на другую базу 1С нужно полностью обнулить привязки, сохранив контент товаров.

Ручная чистка через phpMyAdmin рискованна: легко удалить `posts` вместо `postmeta` и потерять каталог. Этот скрипт делает то же самое предсказуемо, в транзакции, с предварительным подсчётом затрагиваемых строк и подробным журналом.

> [!IMPORTANT]
> Записи `wp_posts` (товары и вариации) **никогда не удаляются**. Скрипт трогает только метаданные, термин-метаданные, служебные опции и кэш-таблицу `wc_product_meta_lookup`. После очистки при следующем обмене с 1С плагин заново создаёт привязки, цены и остатки.

## Возможности

- **Четыре операции**: очистка GUID 1С, очистка цен, очистка остатков и полная очистка (всё в одной транзакции).
- **Предпросмотр перед действием**: количество товаров, GUID, записей цен и остатков, число типов цен и складов в опциях.
- **Автоматическое подключение к БД**: параметры читаются из `wp-config.php` (`DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_CHARSET`, `$table_prefix`); файл ищется в каталоге скрипта и до трёх уровней выше.
- **Транзакционность**: `START TRANSACTION` → операции → `COMMIT`, при любом исключении — `ROLLBACK`.
- **Подготовленные выражения**: PDO MySQL (с фолбэком на mysqli), `PDO::ATTR_EMULATE_PREPARES = false`, имена таблиц проверяются белым списком символов.
- **Доступ по паролю с привязкой к IP**: пароль генерируется при первом запуске, хранится только хеш (Argon2id или bcrypt); успешный IP заносится в ACL и пароль на нём больше не спрашивается.
- **AJAX-интерфейс**: кнопки блокируются и показывают спиннер, страница не перезагружается, ошибки и лог в консоли браузера не стираются.
- **Полный журнал событий**: пошаговые сообщения, нормализованный SQL, число затронутых строк, тайминги каждого запроса; включается переключателем в интерфейсе или параметром `?debug=1`.
- **CLI-режим**: `--status`, `--reset`, `--set-password='…'` для восстановления доступа с сервера.
- **Zero-dependency**: один файл, никаких composer-пакетов, никакой записи в БД WordPress вне перечисленных объектов.

## Что именно изменяется в базе данных

Плагин ItGalaxy хранит данные обмена так (`{prefix}` — ваш `$table_prefix`, обычно `wp_`):

| Данные | Где хранятся | Действие скрипта |
|---|---|---|
| GUID товара/вариации | `{prefix}postmeta.meta_key = '_id_1c'` | `DELETE` для `post_type IN ('product','product_variation')` |
| GUID категории/метки | `{prefix}termmeta.meta_key = '_id_1c'` | `DELETE` всех записей |
| GUID атрибута | `{prefix}woocommerce_attribute_taxonomies.id_1c` | `UPDATE … SET id_1c = ''` |
| Служебные карты GUID | `{prefix}options`: `all1cProducts`, `currentAll1cGroup`, `itglx_wc1c_nomenclature_categories` | `UPDATE … SET option_value = 'a:0:{}'` |
| Цены по типам цен | `{prefix}postmeta.meta_key = '_all_prices'` | `DELETE` |
| Базовые цены | `{prefix}postmeta`: `_price`, `_regular_price`, `_sale_price` | `DELETE` |
| Список типов цен | `{prefix}options.option_name = 'all_prices_types'` | `UPDATE … SET option_value = 'a:0:{}'` |
| Настройки типов цен | `{prefix}options.option_name = 'wc-itgalaxy-1c-exchange-settings'`, ключи `price_type_*` | Удаление ключей по маске `^price_type_\d+(_text\|_summ)?$` с повторной сериализацией |
| Остатки по складам | `{prefix}postmeta.meta_key = '_separate_warehouse_stock'` | `DELETE` |
| Суммарный остаток | `{prefix}postmeta.meta_key = '_stock'` | `DELETE` |
| Список складов | `{prefix}options.option_name = 'all_1c_stocks'` | `UPDATE … SET option_value = 'a:0:{}'` |
| Статусы наличия | `{prefix}postmeta`: `_stock_status`, `_manage_stock`, `_backorders` | `UPDATE` в нейтральные значения `instock` / `no` / `no` |
| Кэш WooCommerce (цены) | `{prefix}wc_product_meta_lookup`: `min_price`, `max_price`, `onsale` | `UPDATE … = 0` |
| Кэш WooCommerce (остатки) | `{prefix}wc_product_meta_lookup`: `stock_quantity`, `stock_status` | `UPDATE … = 0` / `instock` |

Отсутствующие таблицы (`woocommerce_attribute_taxonomies`, `wc_product_meta_lookup`) определяются через `information_schema` и просто пропускаются с записью в журнал.

### Соответствие кнопок и операций

| Кнопка | Что чистит | Когда применять |
|---|---|---|
| **Очистить GUID 1С** | Привязки `_id_1c` (товары, категории, метки, атрибуты) и служебные карты | Дубли товаров, перенос на другую базу 1С, «съехавшие» привязки |
| **Очистить цены** | `_all_prices`, базовые цены, список типов цен, ключи `price_type_*`, кэш цен | Мусорные типы цен, неверные или незакрытые старые цены |
| **Очистить остатки** | `_stock`, `_separate_warehouse_stock`, список складов, статусы, кэш остатков | «Прилипшие» остатки, лишние склады, неверные статусы наличия |
| **Очистить всё** | Все три группы в одной транзакции | Полный сброс перед первым чистым обменом |

## Требования

| Компонент | Минимум | Примечание |
|---|---|---|
| PHP | 8.3 | Используются `enum`, распаковка массивов в списках, `readonly`-свойства, `match` |
| Расширения PHP | `pdo_mysql` **или** `mysqli` | PDO приоритетен; `json`, `session`, `hash` — стандартные |
| MySQL / MariaDB | 5.7 / 10.3 | Нужны `DELETE … INNER JOIN` и транзакции InnoDB |
| WordPress | 5.6+ | Требуется читаемый `wp-config.php` с `define()` |
| WooCommerce | 6+ | Наличие `wc_product_meta_lookup` необязательно |
| Плагин обмена | ItGalaxy «WooCommerce — 1C — Data Exchange» | Схема хранения данных описана выше |
| Права на файлы | запись в каталог скрипта | Для хранилища доступа `.wc1c-cleaner-auth.json` |
| Браузер | любой современный | Нужны `fetch`, `URL`, опционально Clipboard API |

## Установка

```bash
# 1. Скачать файл в корень WordPress (рядом с wp-config.php)
cd /var/www/example.com/public_html
curl -fsSLO https://raw.githubusercontent.com/paulmann/woocommerce-1c-data-cleaner/main/1c-data-cleaner.php

# 2. Права: читаемый веб-сервером файл, каталог доступен для записи
chmod 640 1c-data-cleaner.php
chown www-data:www-data 1c-data-cleaner.php

# 3. Обязательный бэкап базы перед любыми действиями
mysqldump --single-transaction --routines --triggers -u USER -p DBNAME | gzip > backup-$(date +%F-%H%M).sql.gz
```

Откройте `https://example.com/1c-data-cleaner.php` в браузере.

> [!TIP]
> Дополнительно ограничьте доступ на уровне веб-сервера. Nginx:
> ```nginx
> location = /1c-data-cleaner.php {
>     allow 203.0.113.10;   # ваш IP
>     deny all;
>     include fastcgi_params;
>     fastcgi_pass unix:/run/php/php8.3-fpm.sock;
> }
> location ~ /\.wc1c-cleaner- { deny all; return 404; }
> ```
> Apache (`.htaccess`):
> ```apache
> <Files "1c-data-cleaner.php">
>   Require ip 203.0.113.10
> </Files>
> <FilesMatch "^\.wc1c-cleaner-">
>   Require all denied
> </FilesMatch>
> ```

## Первый запуск и пароль доступа

При первом обращении к скрипту:

1. Генерируется пароль из 20 символов (`random_int`, алфавит без визуально похожих знаков).
2. В файл `.wc1c-cleaner-auth.json` рядом со скриптом записывается **только хеш** (`PASSWORD_ARGON2ID`, при отсутствии — `PASSWORD_DEFAULT`/bcrypt), права `0600`, запись атомарная через `.tmp` + `rename`.
3. Текущая сессия авторизуется автоматически, а ваш IP заносится в список доверенных.
4. Пароль показывается **один раз** в баннере с кнопкой копирования и предупреждением: он понадобится для входа **с другого IP-адреса или другого компьютера**.

```text
┌──────────────────────────────────────────────────────────────┐
│ Пароль доступа сгенерирован — сохраните его сейчас           │
│ 7hK2mQ+xR9tLpZ4wNb3e   [Скопировать]                         │
│ Хранится только хеш. Это единственный показ пароля.          │
│ [Я сохранил пароль — скрыть]                                 │
└──────────────────────────────────────────────────────────────┘
```

Модель доступа:

- пароль запоминается в PHP-сессии (cookie `HttpOnly`, `SameSite=Strict`, `Secure` при HTTPS) — в течение сессии не спрашивается;
- успешно авторизованный IP хранится в ACL внутри файла доступа как `hash_hmac('sha256', ip, acl_salt)` со временем жизни 30 суток — с этого адреса пароль не запрашивается даже в новой сессии;
- ограничение на подбор: не более 8 неудачных попыток на сессию плюс задержка 400 мс на каждую;
- кнопка «Выйти и забыть IP» удаляет запись ACL и уничтожает сессию.

> [!NOTE]
> Если сайт работает за реверс-прокси или Cloudflare, включите `Config::TRUST_PROXY = true`, иначе все клиенты придут с одного IP прокси. Не включайте флаг без прокси: заголовок `X-Forwarded-For` подделывается.

## Сброс забытого пароля

Любой сброс очищает `acl_salt`, поэтому привязки к IP аннулируются и пароль потребуется заново всем клиентам. Инструкция также выводится в самом интерфейсе с подстановкой реальных путей.

**Способ 1 — CLI (рекомендуется):**

```bash
php 1c-data-cleaner.php --status                      # состояние хранилища доступа
php 1c-data-cleaner.php --reset                       # сгенерировать новый пароль и напечатать его
php 1c-data-cleaner.php --set-password='НовыйПароль'  # задать свой пароль (минимум 10 символов)
```

**Способ 2 — удалить хранилище (FTP, файловый менеджер панели):**

```bash
rm /var/www/example.com/public_html/.wc1c-cleaner-auth.json
```

При следующем открытии страницы пароль сгенерируется заново и будет показан один раз.

**Способ 3 — файл-маркер сброса (когда нельзя удалять файлы, но можно создавать):**

```bash
touch /var/www/example.com/public_html/.wc1c-cleaner-reset
```

При следующем запросе хранилище пересоздаётся, маркер удаляется автоматически.

## Режим отладки

Включается двумя способами:

- переключателем **«Режим отладки»** в шапке интерфейса — состояние сохраняется в сессии, URL синхронизируется через `history.replaceState`;
- параметром URL: `?debug=1` включает, `?debug=0` выключает (значение записывается в сессию).

В режиме отладки сервер возвращает в JSON массив `log`, который выводится в панель на странице и в консоль браузера через `console.groupCollapsed`:

```text
+    0.31 ms  INFO  Входящий запрос {"method":"POST","php":"8.3.14","debug":true}
+    1.08 ms  INFO  wp-config.php найден {"path":"/var/www/.../wp-config.php"}
+    3.42 ms  INFO  Подключение к БД установлено {"driver":"PDO","port":3306}
+   12.77 ms  INFO  Транзакция START
+   13.05 ms  INFO  Шаг 1/4: GUID товаров и вариаций
+  184.62 ms  DEBUG SQL выполнен {"sql":"DELETE pm FROM `wp_postmeta` pm INNER JOIN …","rows":10432,"ms":171.2}
+  512.90 ms  INFO  Транзакция COMMIT
```

Что попадает в журнал: старт сессии и проверка CSRF, авторизация и работа ACL, поиск и разбор `wp-config.php`, выбранный драйвер, каждый SQL с параметрами и таймингом, границы транзакции, пошаговые сообщения операций, итоги предпросмотра до и после, клиентские события (блокировка кнопок, тайминги запроса, JS-исключения). Пароли, хеши, токены и соли в журнал не попадают — они маскируются как `***`.

## Рабочий процесс в интерфейсе

1. Откройте скрипт, при необходимости введите пароль.
2. Сверьтесь с таблицей **«Текущее состояние»** — сколько GUID, цен и остатков будет затронуто.
3. Отметьте галочку подтверждения (без неё кнопки очистки возвращают ошибку).
4. Нажмите нужную кнопку и подтвердите во всплывающем окне. Кнопка блокируется, показывает спиннер и текст «Выполняется…», остальные кнопки отключаются.
5. В блоке **«Результат»** появится таблица «операция → число строк», время выполнения и количество запросов; таблица состояния обновится без перезагрузки страницы.
6. Запустите обмен с 1С — плагин заново создаст привязки, цены и остатки.
7. Удалите скрипт и файл `.wc1c-cleaner-auth.json` с сервера.

## Архитектура кода

Один файл, строгая типизация (`declare(strict_types=1)`), классы с единственной ответственностью:

| Класс / элемент | Назначение |
|---|---|
| `Config` | Константы: версия, метаданные автора, ключи метаполей и опций, TTL ACL, длина пароля |
| `EventLog` | Журнал событий с таймингами и маскированием чувствительных ключей |
| `Credentials` | Генерация пароля, хеширование, `password_needs_rehash`, ACL по IP, атомарная запись хранилища, обработка файла-маркера сброса |
| `Session`, `Debug` | Инициализация сессии с безопасными cookie, CSRF-токен, разрешение и переключение режима отладки |
| `Auth` | Авторизация по сессии и IP, лимит попыток, одноразовый показ пароля, выход |
| `WpConfig` | Поиск и разбор `wp-config.php` без его подключения (regex по `define()` и `$table_prefix`) |
| `Db` | PDO/mysqli, подготовленные выражения, `ident()` с белым списком символов, транзакции, счётчик и лог запросов |
| `Action` (enum) | `guid`, `prices`, `stocks`, `all` с человекочитаемыми названиями |
| `Cleaner` | Сами операции очистки, пошаговое логирование, пропуск отсутствующих таблиц |
| `Preview` | Подсчёт затрагиваемых сущностей до и после операции |
| JSON API | `POST` с CSRF-токеном: `login`, `logout`, `ack_password`, `set_debug`, `preview`, `guid`, `prices`, `stocks`, `all` |

Ошибки и предупреждения PHP перехватываются обработчиком и попадают в журнал, а не в вывод: `display_errors` выключен, посторонний вывод буферизуется и отдаётся в поле `php_output`, чтобы не портить JSON.

## Безопасность

- Файл даёт прямой доступ к базе магазина — **удаляйте его сразу после работы** вместе с `.wc1c-cleaner-auth.json`.
- Все значения передаются в SQL через параметры; имена таблиц собираются из проверенного префикса.
- `unserialize()` вызывается с `['allowed_classes' => false]` — исключается десериализация объектов.
- CSRF-токен `random_bytes(32)` в сессии, проверка через `hash_equals`, регенерация ID сессии после входа.
- Страница отдаётся с `X-Robots-Tag: noindex, nofollow` и `Cache-Control: no-store`, в `<head>` добавлен `<meta name="robots">`.
- Пароль в открытом виде не хранится и не логируется; в журнале ключи `pass|pwd|secret|token|hash|salt` маскируются.
- Держите файлы доступа вне Git: они уже перечислены в `.gitignore`.

## Бэкап и откат

```bash
# Бэкап только затрагиваемых таблиц (быстро)
mysqldump --single-transaction -u USER -p DBNAME \
  wp_postmeta wp_termmeta wp_options wp_woocommerce_attribute_taxonomies wp_wc_product_meta_lookup \
  | gzip > wc1c-before-clean-$(date +%F-%H%M).sql.gz

# Восстановление
gunzip < wc1c-before-clean-2026-08-27-1542.sql.gz | mysql -u USER -p DBNAME

# После восстановления или очистки — сбросить кэш объектов и пересобрать lookup
wp cache flush
wp wc update_db
```

## Диагностика типовых проблем

| Симптом | Причина | Решение |
|---|---|---|
| «Файл wp-config.php не найден» | Скрипт лежит глубже трёх уровней от корня WordPress | Переместите файл в корень сайта |
| «Не удалось распознать DB_NAME / DB_USER / $table_prefix» | Параметры заданы не через `define()` со строковым литералом (например, через `getenv()`) | Пропишите значения строками или задайте их в `Config` вручную |
| «На сервере не включено ни PDO MySQL, ни mysqli» | Отключены оба расширения | Включите `pdo_mysql` в php.ini / панели хостинга |
| «Недействительный токен сессии» | Сессия истекла, cookie заблокированы или сайт открыт с другого домена | Обновите страницу (F5), разрешите cookie для домена |
| Пароль не запоминается между сессиями | Каталог скрипта недоступен для записи — хранилище ушло в `sys_get_temp_dir()` | Дайте право записи на каталог (интерфейс показывает предупреждение) |
| Кнопка «висит» в состоянии «Выполняется…» | Долгий `DELETE` на большом каталоге или таймаут PHP-FPM | Включите режим отладки и посмотрите тайминги SQL; увеличьте `request_terminate_timeout` |
| После очистки в каталоге пустые цены | Так и должно быть до первого обмена | Запустите обмен с 1С |
| Остатки вернулись «как были» | Работает кэш объектов или CDN | `wp cache flush`, сброс кэша страниц |

## FAQ

**Товары точно не пропадут?** Да. В коде нет ни одного `DELETE FROM {prefix}posts`; удаляются только строки `postmeta`/`termmeta` и обновляются опции и кэш-таблица.

**Можно ли откатить очистку?** Только восстановлением бэкапа. Внутри одного запроса действия выполняются в транзакции, но после успешного `COMMIT` откат средствами скрипта невозможен.

**Подойдёт ли для других плагинов обмена (wc1c, sgtpep/woocommerce-1c)?** Из коробки нет: используются ключи именно плагина ItGalaxy. Адаптация — правка констант в классе `Config`.

**Работает ли на многосайтовой сборке (multisite)?** Скрипт использует один `$table_prefix` из `wp-config.php`, то есть обслуживает основной сайт сети. Для подсайтов нужна доработка префикса (`wp_2_`, `wp_3_` и т.д.).

**Сколько времени занимает очистка?** Основное время — `DELETE … INNER JOIN` по `postmeta`. На каталоге в 20–30 тысяч товаров типично несколько секунд; точные тайминги видны в журнале отладки.

**Нужен ли доступ к админке WordPress?** Нет. Скрипт работает автономно и не загружает ядро WordPress, поэтому не зависит от состояния админки и плагинов.

**Почему интерфейс на AJAX, а не обычная форма?** Чтобы состояние кнопок было видно, а сообщения об ошибках и журнал в консоли браузера не стирались перезагрузкой страницы.

## Вклад в проект

Pull request'ы и issue приветствуются. Пожелания к коду:

- PHP 8.3, `declare(strict_types=1)`, стиль PSR-12, отступ 4 пробела;
- любые значения в SQL — только через подготовленные выражения;
- каждое новое действие должно писать шаги в `EventLog` и корректно работать внутри транзакции;
- в баг-репорт прикладывайте журнал из режима отладки (`?debug=1`), версию PHP, MySQL, WooCommerce и версию плагина обмена — предварительно удалив из лога пути и имена БД, если считаете их чувствительными.
